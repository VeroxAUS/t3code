## Decision

Fork T3 Code. Build the new layer as an **overlay**: new workspace packages plus a handful of small patches at known seams. Merge upstream nightly.

Reasons:

1. T3 already normalises ten harnesses into one event-sourced model with capability flags. That is years of adapter work and it keeps improving upstream for free.
2. The seams we need exist and are narrow: one target-resolution function for delegation, one launch service for threads and scheduled tasks, one capabilities snapshot, one injected instruction string, one event where token usage arrives.
3. Usage windows are already read for every provider, including pooled CLIProxyAPI hubs. The router only needs to turn them into a signal.
4. Mobile and remote come for free, which matters for a cockpit you'll glance at from a phone.

## What we never rebuild

Provider adapters and ACP registry · `delegate_task` / `task_status` / `task_cancel` / `create_threads` / `t3_thread_*` tools · lineage graph and context handoff · worktree lifecycle · scheduled tasks and webhooks · usage scanning and limit probes · auto-resume at limit reset · relay, tunnel, mobile · OAuth for outside agents · the evals package shape.

Also lean on provider-native features instead of re-implementing them: Claude Code subagents (`model`, `effort`, `maxTurns`, `isolation: worktree`), agent teams, Workflow tool, `/batch`, `/goal`; Codex `[agents]` config (`default_subagent_model`, `default_subagent_reasoning_effort`, `max_concurrent_threads_per_session`).

## Fork strategy (the part that decides whether this survives)

Upstream ships several breaking nightlies a day and a tagged release every week or two. The overlay tracks the **tags**, not nightly `main`, and has to be cheap to merge at each tag.

- **Branches.** `upstream/main` mirrored to `main`. Our work on `overlay/main`, created from the upstream `v0.1.3` tag commit and the fork's **default branch** (scheduled workflows run only from the default branch). Step branches off `overlay/main`, always from a fresh fetch. `fork-main` and `usage-strip` are archived; their useful pieces are ported in Phase 0.
- **Tag merge job, not rebase.** A GitHub Action checks nightly for a new upstream release tag; when one exists it merges the tag into `overlay/sync` (appending to the existing branch while its PR is open; never a rebase or force-push), writes a `sync-<tag>.md` handoff, and opens or updates a PR into `overlay/main` with a PAT so the required checks run; it opens an issue listing the conflicting files when the merge fails, and fails loudly without the token. Overlay commits stay findable with `git log --first-parent`.
- **Manifest, not a number.** Every upstream file the overlay changes is listed in `docs/overlay/CHANGES.md` with its reason; `scripts/overlay-check.ts` reconciles the manifest with each PR's changed upstream paths in CI. `// overlay:` markers go on changed lines where the file type allows comments. Logic lives in `packages/routing`, `apps/server/src/routing/`, `apps/web/src/components/team/`, `evals/routing`; the hook patches are few, the registration edits (UI entry points, package scripts, knip, settings navigation) are more, and the manifest is what keeps merges findable.
- **Feature flags** under one namespaced settings key `overlay` (`overlay.routing.enabled`, `overlay.routing.mode: "off" | "shadow" | "enforce"`, `overlay.cockpit.teamView`). Off by default so a half-merged overlay can ship dark, and one key keeps an upstream build reading an overlay `settings.json` from tripping over unknown fields.
- **Disable upstream auto-update and analytics** in overlay builds (Phase 0 step 2), or the desktop app will replace itself with a stock nightly.
- **Upstream what's small.** A "target policy hook" and "capabilities carries usage" are tiny and generic; try upstreaming them. If upstream declines, we carry them.
- **Exit hedge.** `packages/routing` is pure TypeScript with no T3 imports: inputs are plain objects (windows, rates, task role, tier request), output is a decision with reasons. If T3 drifts beyond repair, the router and the pipeline templates move to Emdash or Paperclip in a week; only the UI and the ledger are T3-shaped.

## Things that are already better upstream than anything we'd write

- `ThreadManagementService` as the single application boundary for WebSocket and MCP commands. Our hooks go behind it, not around it.
- The capability system: route on flags (`supportsModelSwitchInSession`, `canForkThread`), never on provider names.
- `UsageLimitRecoveryWorker`: when a thread errors with `usage_limit` it snoozes and resumes at `usageLimitResetAt`. The router's "exhausted" band plugs into that instead of inventing a queue.
