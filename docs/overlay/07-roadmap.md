# 07 · Roadmap and implementation steps

Effort is for one developer driving agents through T3 itself, including tests and merges. Each phase ships behind a flag and is usable on its own. Phase order is 0, 0b, 1, 2, 3, 4, 5, 6. Order matters: nothing after Phase 1 is testable without the ledger and pressure signal. A phase is complete only when its review handoff records `status: passed` (`10-execution-plan.md` §2); the design round that opens the next phase folds that phase's promoted ideas (table at the end) into its numbered steps and writes that phase's step prompts under `prompts/phase-N/`. Phase 0's step prompts are already in `prompts/phase-0/`.

## Phase 0b · Contract spikes (3–4 days)

Five investigations against the checked-out revision, each producing a doc under `docs/overlay/spikes/` with reproducible commands and results. Record `git rev-parse HEAD` and provider/runtime versions in each spike; if a sync lands between steps, record the changed baseline and recheck affected assumptions. These are contract probes, not the ledger, router or permission enforcement implementation. Step prompts live in `prompts/phase-0b/`.

### Capture scope and evidence

Live coverage is Claude subscription, Codex subscription and Antigravity with Google AI Pro; `Claude Credit` is a separate Claude instance for step 5's billing test. Antigravity is deliberately included now to assess a cheaper route for lighter work before routing is designed. The developer reports a $25/three-month trial offer; this is context, not a verified price or permission to purchase. Use the existing Antigravity provider, Google's official ACP runtime and personal Google sign-in, not an API-key substitution. Record the actual available Gemini model, instance and credential kind. T3's route is described in `docs/user/providers-antigravity.md`; upstream [discussion #23268](https://github.com/pingdotgg/t3code/discussions/23268) points to [Google's clarification](https://discuss.ai.google.dev/t/supported-gemini-subscription-access-for-a-third-party-vs-code-extension/189889/4). The discussion identifies the route, not proof of this account's capabilities.

Replay is a synthetic development provider and is never live billing evidence. OpenCode 2 and other ACP agents get source/fixture coverage where available; mark live coverage untested unless the developer enables an instance. Antigravity uses the shared ACP adapter, but a result for it does not prove every ACP agent. Cursor, Grok and other providers remain outside required live coverage.

Run live probes from a T3 session with launch/delegation tools connected to the isolated dev environment; a plain CLI without those tools is insufficient. Use isolated development state and disposable workspaces; never run a spike against the live T3 database. The developer supplies any account setup, billing-page readings and browser actions. Ask before browser/computer use. Keep secrets, auth callbacks and private prompts out of committed fixtures; retain only token fields, stable anonymized identities, configuration kind and relevant results. Missing credentials or tooling is recorded as missing evidence, never replaced by Replay proof or a silent provider switch.

### Steps

1. **Token semantics.** Capture a small live Haiku 5.5 turn on the Claude subscription instance, a Luna turn on Codex, and a turn on an available Gemini model through Antigravity/Google AI Pro. Record native usage, normalized `turnTokenUsage`, cumulative-versus-delta behavior, completeness, cache/reasoning inclusion and native-subagent scope. Compare Replay and available OpenCode 2/ACP fixtures, explicitly labelled synthetic or recorded. Add a pure disjoint-bucket function and hand-computed USD cases in `packages/routing/src/costs.ts` and `costs.test.ts`, with no T3 imports or live rate fetching. Pin fixture rates and provenance; unknown or unavailable counters are not zero spend. A real adapter mismatch is a finding with a proposed boundary normalization, not permission to rewrite the adapter. Output: `spikes/token-semantics.md`. This step does not wait for step 5.
2. **Replay durability.** In `apps/server/src/routing/ReplayDurability.spike.test.ts` only, prototype durable turn identity, idempotent cumulative replacement and a transactional cursor against the real event-store/SQL test layers. Prove restart mid-turn, duplicate delivery, late correction, partial-to-complete usage, rollback between row/cursor writes and rebuilt totals equal live application. Include a provider without strong native turn identity; distinguish missing usage from zero. No production service, migrations or ingestor hook yet. Output: `spikes/replay-durability.md`, including which persisted events can reconstruct usage and which cannot.
3. **Permissions.** Run disposable children on Claude, Codex and Antigravity with `interactionMode: plan` and separately `runtimeMode: approval-required`, plus supported combinations. Record the requested and effective modes, direct-file and shell-write attempts, approval denial/allow behavior and unsupported settings. Verify file state after each probe; model refusal alone proves no sandbox guarantee. OpenCode is optional if enabled. Classify each capability as runtime-enforced, approval-gated, prompt-only, unsupported or untested; never label all plan modes read-only. Output: `spikes/permissions-map.md`, which the role briefs will cite.
4. **Candidate workspaces.** Prove `t3_thread_launch` with the structured `workspaceStrategy: { type: "worktree", baseRef: <SHA>, ... }` and `existing_worktree` attach against a disposable project. Record requested SHA, actual HEAD, worktree path and tracked/untracked/ignored sentinel state. A fresh verifier checkout must use the candidate commit and must not inherit the writer's dirty files; attaching an existing worktree is not isolation. Record setup-script effects separately from Git copying and clean up only resources created by this spike. Output: `spikes/candidate-workspace.md`, with an exact verifier recipe.
5. **API credit (#37).** Use the configured `Claude Credit` instance (decision 15; `10-execution-plan.md` §8.1). Capture fresh, isolated before/after Promotional-credit and Max-window readings around one Haiku 5.5 turn, one Sonnet 5.5 turn and one title regeneration; capture the turns' usage as additional step-1 fixtures where useful. Separately submit and retrieve one Haiku Message Batches request using the same key through a temporary script. Record request IDs without secrets, rate/date, billing source, actual charge when available, API-equivalent arithmetic separately, and batch discount against the same model's standard rate. Verify instance-key/config-directory isolation without printing credentials. Refresh vendor billing eligibility and rate references during this step; SDK implementation alone does not establish credit eligibility. Output: `spikes/api-credit.md`, with `go` or `no-go` for in-T3 credit routing and a separate batch result. Rounded balances, delayed reporting or concurrent usage are insufficient attribution: mark the result inconclusive and keep the gate `no-go` until resolved, rather than spending repeatedly to force a visible delta.

### Exit and design decisions

All five spike docs carry commands, results, baseline/version and explicit coverage gaps; focused tests pass. Negative contract findings are useful results, not passing claims about unsupported capabilities. A required live probe that was never run remains incomplete and needs an explicit developer deferral before review can pass. Inconclusive billing keeps the credit gate closed; a demonstrated limitation can complete the investigation with `no-go`.

Step 5 writes the complete handoff with each exit criterion, #37's result, and an assumption-disposition table for 03, 04 and 05 (confirmed, contradicted or unresolved, with evidence). The Phase 1 design round resolves the implications with the developer before implementing them. `decisions.md` records developer-accepted changes only; observations and unanswered proposals stay in spikes/handoffs. `go` admits the in-T3 credit steps in Phases 1–3; `no-go` excludes them until reconsidered. The external digest requires its own successful batch evidence regardless of the T3 result.

## Phase 4 · Delegation engine (3–4 weeks)

Steps

1. `packages/routing/src/pipelines.ts`: templates (`feature`, `bugfix`, `research`, `design`, `sweep`, `best-of-n`) and role briefs; `.t3/roles/*.md` override loader (server, project-scoped); a persisted `pipeline_runs` record (root thread, template, current step, base SHA, candidate SHA, worktree path, approvals, attempts per step) updated by the templates through a small MCP tool. It is a record the invariants are checked against, not a workflow engine.
2. Role defaults applied in `decide` (tier, effort, runtime ceiling) and brief injected into the child's first message (extend the existing role-instruction path in `delegateTask`).
3. `/pipeline <template> <request>` composer command + palette entry: expands the template into the root prompt with the request (or the body of a referenced `#issue`) as the first brief; argument rules in 05 "Pipeline templates". MCP `pipeline_start` tool that does the same for agents. Webhook recipe: GitHub label → scheduled-task webhook → `t3_thread_launch` with the template (docs only; the plumbing exists).
4. `Witness.ts`: stall detection, parent notification via the delegated-question path, amber badge, optional cancel; settings `overlay.witness: { stallMinutes, onStall }` with decoding defaults.
5. Server caps, each separate: `maxConcurrentChildrenPerRoot`, `maxChildrenLifetimePerRoot`, `maxAttemptsPerStep`, `maxDepth`, the global `overlay.limits.maxConcurrentChildren`, `maxTurnsPerChild` where the provider supports it, and `maxElapsedMinutesPerChild` with interrupt.
6. `MergeQueue.ts`: serialised lane (rebase → test → `merge-tree` → merge/PR), bounce on conflict; MCP `merge_queue_enqueue`; reactor on `subagent_result`.
7. Best-of-N: template that uses `create_threads`/`t3_thread_launch` with worktrees plus a judge delegate; cleanup through existing worktree removal.

8. Promoted ideas for this phase (table at the end), one PR each.
9. Template eval in `evals/routing`: five runs of the `feature` template on Sonnet 5.5 against a fixture repo, plus scenario runs for restart mid-pipeline, cancellation, duplicate completion delivery, a rejected approval and a verify failure. Invariants are checked against the `pipeline_runs` record: no merge without a passed verify and a reviewed candidate SHA, no skipped approval, correct behaviour in every scenario. Ordering adherence (steps appear as child threads in order, verifier receives no parent history) is the statistical part.

Tests: template expansion snapshots, witness state machine, merge queue with a fixture repo (`it.live`, subprocess fixture rule), caps.

Exit: `/pipeline feature` on a real ticket runs plan → implement → verify → review → merge with two human checkpoints and every step visible as a child thread; invariants hold in 5 of 5 runs and every scenario; ordering adherence 4 of 5.
